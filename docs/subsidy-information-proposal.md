# 補助金情報取得・判定 提案書

## 1. 提案概要

### 目的

RENOの相談内容から利用可能性のある住宅リフォーム支援制度を検索し、制度の対象候補・不足条件・対象外を根拠付きで案内する。AIの記憶だけで制度名、補助額、期限を回答することは禁止し、公式情報を登録した制度DBとルール判定を正とする。

### 今回の提案範囲

- 初期対象は国の住宅省エネ系制度とする。
- 自治体制度は住所（都道府県・市区町村）を取得できるようになった後、段階的に追加する。
- 補助金の交付を保証する機能ではなく、「対象候補の検索・確認事項の提示」までを対象とする。
- 申請書の作成・代理申請・最終的な交付可否の判断は対象外とする。

## 2. 初期に調査・登録する制度

| 制度 | 主な対象 | RENOでの関連機能 | 公式情報 |
|---|---|---|---|

| 先進的窓リノベ2026事業 | 高断熱窓・ガラス・ドアへの改修 | 窓・開口部の画像診断、登録製品照合 | [環境省・公式サイト](https://window-renovation2026.env.go.jp/) |
| 給湯省エネ2026事業 | 高効率給湯器の設置 | 給湯器の製品・性能要件照合 | [経済産業省・公式サイト](https://kyutou-shoene2026.meti.go.jp/) |
| 賃貸集合給湯省エネ2026事業 | 賃貸集合住宅の給湯器交換 | 賃貸・集合住宅・所有者条件の判定 | [住宅省エネ2026公式](https://jutaku-shoene2026.mlit.go.jp/) |

## 3. 利用者から収集する情報

不足情報がある場合、AIは補助金額を推測せず、以下の追加質問を行う。

| 項目 | 必須度 | 例 |
|---|---|---|
| 工事予定地域 | 必須 | 東京都、横浜市 |
| 住宅区分 | 必須 | 戸建、マンション、賃貸集合住宅、非住宅 |
| 所有・居住関係 | 必須 | 所有者、賃借人、発注者 |
| 新築・既存 | 必須 | 既存住宅 |
| 住宅の築年・完成時期 | 制度依存 | 2010年完成 |
| 工事内容 | 必須 | 内窓設置、床断熱、給湯器交換 |
| 製品名・型番・性能 | 製品制度で必須 | 窓の製品型番、給湯器の性能区分 |
| 契約・着工・完了予定日 | 必須 | 2026年7月契約、8月着工 |
| 世帯条件 | 制度依存 | 子育て世帯等 |
| 他制度の利用状況 | 必須 | 他の国費補助との併用有無 |

## 4. 制度DBの最小構成

制度DBは、素材カタログDBとは分離した `subsidy_program` 系のデータとして管理する。制度の変更履歴を残し、過去の回答を後から追跡できるようにする。

| テーブル／項目 | 主な内容 |
|---|---|
| `subsidy_program` | 制度ID、制度名、実施主体、対象地域、年度、ステータス |
| `subsidy_requirement` | 対象住宅、対象者、工事、性能、築年、契約・着工条件 |
| `subsidy_amount_rule` | 補助率、上限、最低額、単位、計算条件 |
| `subsidy_compatibility` | 併用可否、重複不可の制度ID、優先ルール |
| `subsidy_schedule` | 受付開始・終了、予約期限、予算到達時の扱い |
| `subsidy_source` | 公式URL、原文またはPDF、取得日時、確認者、ライセンス・利用条件 |
| `subsidy_revision` | 変更差分、旧版、新版、承認者、公開日時 |

金額・期限・性能値はAIの文章ではなく、DBの構造化項目から表示する。出典が確認できないレコードは公開状態にしない。

## 5. 判定フロー

1. Lambdaが会話から条件を抽出し、入力JSON Schemaを検証する。
2. 必須条件が不足している場合は、AIに追加質問を生成させる。
3. 条件が揃ったら制度DBを地域・年度・工事種別で検索する。
4. ルールエンジンが対象要件、性能、期間、併用条件、予算状況を判定する。
5. アプリが「対象候補」「条件不足」「対象外」に分類し、制度名・概算額・不足条件・出典URL・確認日を表示する。
6. 公式情報の期限切れ、取得失敗、矛盾がある場合は「要確認」とし、断定表示を停止する。

AIは条件抽出・追加質問・説明文の生成だけを担当する。制度検索、金額計算、期限判定、併用判定はアプリとDBで実施する。

## 6. 情報取得方式（MCPを含む）

### 推奨構成

- 初期構成はEventBridge Scheduler、Lambda、S3、DynamoDBで構成する。
- EventBridge Schedulerが定期的にLambdaを起動する。
- Lambdaは公式Webページ・PDF・APIを取得し、取得した原文をS3へ保存する。
- Lambdaは取得内容を正規化し、差分・更新履歴をDynamoDBへ保存する。
- アプリの判定処理は、担当者が承認したDynamoDBの公開データだけを参照する。
- S3は公式原文、PDF、取得時刻、ファイルハッシュを保存する監査・再解析用領域とする。

- 第一優先：各省庁・事務局の公式API、CSV、公開PDF、公式Webページ。
- 第二優先：公式ページを定期取得するLambdaジョブ。HTML/PDFの取得後、差分を保存し、人が承認して公開する。
- MCP：公式情報を検索・取得する手段が確認できた場合のみ、取得アダプターとして採用する。MCPの回答をそのまま表示せず、取得元URLと取得日時を必須にする。
- 自治体情報：環境省の検索ページを入口にし、最終的には自治体公式ページを出典として登録する。

現時点では「国の補助金を横断して自由利用できる単一の公式MCP」が存在することを前提にしない。ライセンス、利用規約、アクセス制限を制度ごとに確認し、確認できない情報源は本番判定に使用しない。

#### 初期AWS構成

```text
EventBridge Scheduler（1日1回）
        ↓
Lambda（取得・正規化・差分検出）
        ├─ S3（公式HTML／PDF／取得履歴）
        └─ DynamoDB（制度情報／下書き／承認済み／履歴）
```

S3への保存は原文の保全を目的とし、アプリの検索・判定はDynamoDBを参照する。取得失敗時はDynamoDBの前回承認済みデータを自動更新せず、「要確認」として通知する。

### 更新運用

| 対象 | 推奨頻度 | 公開条件 |
|---|---|---|
| 受付期間・予算状況 | 1日1回 | 差分確認者の承認後 |
| 対象要件・補助額 | 週1回＋公式更新通知時 | 公式資料と照合後 |
| 自治体制度 | 月1回 | 自治体公式ページ確認後 |
| 取得エラー | 即時通知 | 前回の有効データを表示し「要確認」を付記 |

## 7. システム要件・精度担保

- すべての制度レコードに公式URL、確認日、有効開始・終了日を持たせる。
- 期限切れレコードは自動的に検索対象外にする。
- 受付終了・予算到達情報を取得できない場合、補助額を表示せず「公式確認が必要」とする。
- 制度DBの条件判定結果と、AIが表示した文章の内容をテストで照合する。
- 補助金額・期限・対象可否の根拠を監査ログに保存する。個人情報や画像はログに保存しない。
- 制度更新前後の回帰テスト（対象、対象外、条件不足、併用不可、受付終了）を自動実行する。

### 受入基準

| 指標 | 目標 |
|---|---:|
| 出典URL表示率 | 100% |
| 期限切れ制度の誤表示 | 0件 |
| DB金額と表示金額の一致率 | 100% |
| DB判定と表示判定の一致率 | 100% |
| 条件不足時の断定表示 | 0件 |
| 取得失敗時の要確認表示 | 100% |

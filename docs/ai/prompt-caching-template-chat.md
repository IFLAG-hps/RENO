# テンプレチャット（定型アクション）のキャッシュ活用検討

## 結論

テンプレチャットはキャッシュ活用によるコスト削減が可能。ただし、OpenAIのPrompt Cachingで安くなるのは「入力プロンプトの再利用部分」であり、応答そのものを再利用する機能ではない。

RENOでは、次の二段構えを推奨する。

1. 共通のシステム指示・定型アクション定義・出力形式を毎回同じプレフィックスとして送信し、Prompt Cachingを利用する。
2. 個別情報を含まない完全に同一の定型問い合わせだけ、アプリケーション側で応答を再利用する。

写真、部屋、予算、会話履歴などが変わる診断・見積もり結果は、ユーザー間で応答を共有しない。誤った提案の再利用や個人情報の混入を避けるため、原則としてモデルを呼び出し、共通プレフィックス部分だけをキャッシュ対象にする。

## 公式仕様の要点

OpenAIの公式ドキュメントによると、Prompt Cachingは同一のプロンプトプレフィックスを再利用し、キャッシュされた入力トークンにはモデルごとの割引料金が適用される。割引は最大90%で、対応モデルではデフォルトで有効。キャッシュヒット率はPrompt Caching Dashboardとレスポンスの`usage.input_tokens_details.cached_tokens`で確認できる。

- キャッシュ再利用には、対象プレフィックス全体の一致が必要。モデル、ツール定義、構造化出力スキーマ、推論設定、会話履歴など、前方にある内容が変わると後続部分もヒットしない。
- キャッシュ可能な最小長はモデル依存。GPT-5.6以降は可視入力1,024トークン、それ以前のモデルは通常2,048トークンが目安。
- キャッシュは永続保存ではない。GPT-5.6以降のTTLは`30m`が基本で、それ以前のモデルはモデル・組織設定により保持時間が異なる。
- `prompt_cache_key`は同じプレフィックスを同じキャッシュグループへ寄せるためのルーティング補助であり、ヒットを保証するものではない。
- キャッシュは入力コストと入力処理時間を削減するが、出力トークン料金、画像生成、S3・Lambda等の費用は削減しない。

出典: [OpenAI API Prompt caching（公式ドキュメント）](https://developers.openai.com/api/docs/guides/prompt-caching)

## RENOへの適用評価

### 効果が高い候補

| 定型アクション | キャッシュ適性 | 理由 |
| --- | --- | --- |
| 相談内容の整理・次に聞く質問 | 高 | 共通指示と出力形式が長く、利用回数が多い。ユーザー入力だけを末尾に置ける。 |
| 画像診断結果の説明 | 中 | 診断ルール・JSONスキーマは共有できるが、画像と診断対象は毎回変わる。 |
| 概算見積もりの説明 | 中 | 見積もりルールは共有できるが、部屋・仕様・予算は毎回変わる。 |
| 「担当者に相談する」受付確認 | 低〜中 | 固定文面ならアプリ側で返せる。個別情報を要約する場合はモデル呼び出しが必要。 |
| 同一ユーザーの短時間の追質問 | 高 | 直前までの共通コンテキストが一致しやすい。ただし履歴が長くなると一致範囲が縮む。 |

### 効果が低いケース

- 定型文が短く、キャッシュ可能な最小トークン長に達しない場合。
- ボタンごとにシステム指示の文言、ツール定義、JSONスキーマの順序が異なる場合。
- 毎回、時刻・乱数・ユーザー情報などをプロンプトの先頭側へ挿入する場合。
- 低頻度の操作で、TTL内に同じプレフィックスが再利用されない場合。

## 推奨するプロンプト構成

入力を「固定部分 → 変動部分」の順に統一する。

```text
[固定] RENO共通の役割・安全ルール
[固定] 定型アクションの手順・出力JSONスキーマ
[固定] 共通の商品・施工ルール
[変動] ユーザーの部屋、予算、写真、現在の会話
```

現在の`backend/src/handler.py`は、`system`と会話履歴を1リクエストに詰めて送っている。今後テンプレアクションを導入する際は、アクションIDをサーバー側の許可リストで解決し、クライアントから任意のシステムプロンプトを受け取らない設計にする。

GPT-5.6以降でのResponses APIの概念例は次のとおり。

```json
{
  "model": "${OPENAI_MODEL}",
  "input": [
    { "role": "developer", "content": [{ "type": "input_text", "text": "共通指示 + 定型アクション定義" }] },
    { "role": "user", "content": [{ "type": "input_text", "text": "今回の部屋・予算・質問" }] }
  ],
  "prompt_cache_key": "reno:template:estimate:v1",
  "prompt_cache_options": { "mode": "implicit", "ttl": "30m" },
  "max_output_tokens": 500,
  "store": false
}
```

`prompt_cache_options`の利用可否・指定方法は実際に採用するモデルのAPI仕様に合わせて確認する。現在の既定値である`gpt-5-mini`のような旧世代モデルでは、明示的ブレークポイントや`ttl`ではなく、モデルが対応する暗黙キャッシュと`prompt_cache_retention`を使う形になる可能性がある。対応しないモデルでは、固定プレフィックスの順序を統一するだけでも暗黙キャッシュのヒット率改善が期待できる。

## アプリケーション側の応答キャッシュ

以下の条件をすべて満たす操作だけ、DynamoDBまたは短期TTLのキャッシュを検討する。

- 入力が完全一致する。
- 最新情報、個人情報、画像、権限情報を含まない。
- 応答がユーザーごとに変わらない。
- キャッシュキーにテンプレートバージョンを含める。

例: 「リフォーム相談では何を準備すればよいか」のような一般案内は`template_id + locale + version`をキーにできる。一方、「この写真の浴室を診断して」「この内容で見積もって」は画像・入力内容・会話・ユーザー単位をキーに含めても、保存期間を短くし、原則共有しない。

固定の受付確認、入力不足時の案内、利用上限メッセージなど、モデル品質が不要な文言はモデルを呼ばずLambdaで返す。これはPrompt Cachingより確実に1回分のモデル費用を削減できる。

## コスト試算の考え方

現行の売上試算ページでは、チャット入力を1回12,000トークンとしている。このうち、共通の定型プレフィックスが8,000トークン、変動入力が4,000トークン、キャッシュヒット率が80%だと仮定すると、平均キャッシュ利用量は6,400トークン/回になる。

入力費用の削減率は次式で見積もる。

```text
削減率 ≒ 共通プレフィックス比率 × キャッシュヒット率 × (1 - キャッシュ入力単価 / 通常入力単価)
```

ただし、実際の削減率はモデルのキャッシュ入力単価、キャッシュ書き込み料金、TTL内の再利用率、ルーティングによるミスを含めて計測する。出力が大半を占める短いチャットでは、入力キャッシュだけでは総額の削減幅は限定的になる。

## 実施順序

1. 定型アクションを`template_id`で管理し、固定指示・スキーマ・変動データを分離する。
2. アクションごとに`prompt_cache_key`を安定した命名で付与する。例:`reno:template:diagnosis:v1`。
3. `cached_tokens`、総入力トークン、出力トークン、アクションID、モデルをCloudWatch等へ記録する。プロンプト本文や画像・個人情報はログへ出さない。
4. 1〜2週間、または十分なリクエスト数を集め、実測のヒット率と入力費用を比較する。
5. ヒット率が低いテンプレートは、先頭の可変情報、短すぎる固定文、モデル混在、TTL超過を確認する。
6. 固定案内だけアプリ側応答キャッシュへ移し、診断・見積もりなど個別性の高い処理はモデル応答キャッシュの対象外とする。

## 採否判断

定型アクション向けPrompt Cachingは採用候補とする。ただし、いきなり全チャットへ適用せず、まず「相談内容の整理」などテキスト中心で利用頻度の高い1テンプレートを対象に計測する。目標値は、固定プレフィックス1,024〜2,048トークン以上、キャッシュヒット率70%以上、入力トークン費用の実測削減を確認できることとする。

画像診断・見積もりは、共通指示のPrompt Cachingのみ適用し、個別の診断結果や見積もり結果をユーザー間で共有する応答キャッシュは採用しない。

# 画像診断AIモデル検証実験計画書

## 1. 目的

検証環境で実際のアプリケーションフローを稼働させ、画像診断AIの候補モデルを「コスト・精度・速度」の3軸で比較する。素材カタログDBと連携し、AIが登録外の素材を提示しないことも自動テストで確認する。

本計画は承認後すぐに実行できるよう、テストデータ、テストコード、測定項目、合格基準を定義する。本番導入の可否は、実験結果と運用リスクを確認したうえで別途判断する。

## 2. 実施条件

- 実施環境：既存の検証環境（アプリ、API、AI接続、ログ基盤）
- 実行方式：コード化した自動テストをCIまたはローカルコマンドで実行
- DB：素材カタログDBの検証用データを投入し、検索・ID照合・公開状態検証まで接続
- 対象モデル：同一画像・同一プロンプト・同一出力スキーマで比較
- 本番データ：使用しない。公開画像または利用許諾済み・匿名化済み画像のみ使用

## 3. 比較対象モデル

| 比較軸 | モデル | 想定する役割 | 公式単価（2026-09-02時点） |
|---|---|---|---|
| コスト | GPT-5.6 Luna (`gpt-5.6-luna`) | 低コスト・大量処理候補 | 入力 $0.20／出力 $1.20 per 1M tokens |
| 精度 | GPT-5.6 Sol (`gpt-5.6-sol`) | 複雑な画像の精度基準候補 | 入力 $4.00／出力 $20.00 per 1M tokens |
| 速度 | GPT-5.4 nano (`gpt-5.4-nano`) | 低遅延の分類・抽出候補 | 入力 $0.20／出力 $1.25 per 1M tokens |

参考： [OpenAI公式モデル比較](https://developers.openai.com/api/docs/models/compare)

## 4. テストデータ準備

### 4.1 データセット

- 初回スモークテスト：30件（各部位・状態を最低限含める）
- 本試験データ：200件を目標（床、壁、天井、窓、建具、キッチン、浴室、トイレを各25件）
- ホールドアウト：50件。本試験の結果を見た後も内容を変更しない
- 画像条件：JPEG／PNG、長辺1,024pxへ正規化。1画像・複数画像ケースを分けて管理

### 4.2 収集方法

1. 再利用条件が明示された公開画像を原典ページから収集する。
2. 出典URL、作者、ライセンス、取得日、商用利用可否をmanifestに保存する。
3. 人物、住所、表札、車両番号などが写る画像は除外またはマスキングする。
4. 施工会社・社内画像は利用許諾を取得し、匿名化したものだけを追加する。
5. 同一画像・類似画像を除外し、テスト結果を見てデータを差し替えない。

### 4.3 ラベル

最低限、部位、素材種別、劣化状態、判定不能理由、正解素材ID（DB登録済みの場合）をmanifestに記録する。2名が独立して確認し、相違は施工担当者が裁定する。

## 5. 素材カタログDBとの連携要件

素材カタログDBの設計は [material-catalog-db.md](./material-catalog-db.md) を正とする。

1. テスト開始前に、公開状態の素材・非公開素材・廃番素材・存在しない素材IDを検証用DBへ投入する。
2. 検索APIが返した候補IDだけをAIへの入力候補にする。
3. AIの出力をJSON Schemaで検証する。
4. バックエンドでID、公開状態、カテゴリ、仕様を再照合する。
5. 未登録ID、非公開ID、仕様不一致は表示せず「要確認」にする。

## 6. 自動テスト仕様

テストコードはモデルごとに同じfixtureを読み込み、結果JSONと計測メタデータを保存する。

| テストID | 内容 | 合格基準 |
|---|---|---|
| IMG-001 | 画像入力・診断APIの正常系 | 200応答、必須項目が存在 |
| IMG-002 | JSON Schema検証 | 100%合格 |
| IMG-003 | 部位・状態ラベルの比較 | 正解率をモデル別に集計 |
| IMG-004 | 不鮮明・判定不能画像 | 「要確認」を返し、断定しない |
| CAT-001 | 登録素材IDの推薦 | 登録済み公開IDのみ |
| CAT-002 | 架空・非公開・廃番IDの拒否 | 表示率0% |
| CAT-003 | DB仕様との一致 | 商品名・型番・価格・性能がDBと一致 |
| ROUTE-001 | 信頼度不足の再判定 | 上位モデルへ遷移 |
| ROUTE-002 | APIエラー・タイムアウト | 1回再試行後に要確認へ遷移 |
| COST-001 | トークン・API費用記録 | 全リクエストで記録 |
| PERF-001 | レイテンシ計測 | 平均・P95を記録 |

## 7. 測定項目と合格基準

| 指標 | 目標・判定方法 |
|---|---|
| 部位の正答率 | モデル別に集計。初回目標80%以上 |
| 劣化状態の正答率 | モデル別に集計。初回目標70%以上 |
| 根拠のない断定率 | 10%以下を目安。超過時は要改善 |
| 架空素材表示率 | 0%（必須） |
| DB仕様一致率 | 100%（必須） |
| JSON Schema合格率 | 99%以上 |
| 平均／P95応答時間 | 平均15秒／P95 30秒以内を目安 |
| API費用 | モデル・シナリオ別に算出 |
| エラー・タイムアウト率 | 5%以下を目安 |

## 8. 自動モデル切替テスト

- 通常・単一部位：Lunaを呼び出す。
- 不鮮明、複数部位、信頼度不足：Solへ再判定する。
- JSON検証失敗、タイムアウト：1回再試行し、再失敗は要確認とする。
- 切替理由、モデルID、再判定有無、費用、結果をテストログへ保存する。

## 9. 実行手順

1. 承認後、検証用DBへfixtureを投入する。
2. manifestと画像をテスト用ディレクトリへ配置する。
3. APIキー、モデルID、実行上限を環境変数で設定する。
4. スモークテスト30件を実行し、接続・DB照合・ログを確認する。
5. 本試験200件を3モデルで自動実行する。
6. ホールドアウト50件で再実行し、結果を固定する。
7. レポートを出力し、モデル構成と自動切替条件をレビューする。

## 10. 出力物

- モデル別のテスト結果JSON／CSV
- モデル別のAPI費用・トークン使用量
- 平均・P95レイテンシ、エラー率
- 部位・劣化状態の正答率、誤断定率
- 素材ID・DB仕様の照合結果
- 自動切替の発生率と理由
- 採用候補・不採用理由・残課題をまとめた報告書
